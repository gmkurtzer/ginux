# C3 Verification: Alpine Shell Container

**Implementation status:** In progress.

## Pinned image input

C3 starts with the unmodified Alpine 3.24.2 x86-64 image and its configured
`/bin/sh`. The profile pins the architecture-specific manifest, config, layer,
and expanded rootfs digests; no container receives an implicit image.

```text
configured: docker.io/library/alpine:3.24.2
resolved: docker.io/library/alpine@sha256:d56c381f961d307a21b3ca004cf1e3910f106644aefb1f43e654c8a56c4fd395
platform: linux/amd64
init: /bin/sh
```

Prepare, verify, build, and boot it on macOS or Linux with one command:

```sh
make run
```

The command downloads the pinned image only when it is not already cached.
`make test-alpine` performs both the non-interactive QEMU ingestion gate and a
real musl/BusyBox shell transcript. The narrower image and build targets remain
available for diagnostics, while `make build` remains independent of Docker
and does not silently select an image.

## Completed ingestion boundary

The preparation path pulls the exact linux/amd64 manifest, retains the OCI
layout, verifies the manifest/config/layer descriptors, expands the layer, and
verifies its OCI diff ID. The Alpine-enabled boot carries that verified rootfs
as a read-only boot object. The kernel independently verifies the full rootfs
SHA-256, validates bounded tar structure and paths, resolves
`/bin/sh -> /bin/busybox`, and validates the BusyBox and musl ELF inputs.

This is a temporary local-input path for execution development, not the final
runtime registry pull. The final path resolves the configured reference over
control-domain DNS/TCP/TLS, streams objects through transactional boot-local
storage, verifies each digest, and atomically publishes the image. Failed or
partial pulls never become visible.

## Current execution boundary

Alpine BusyBox and its musl loader are now accepted by a separate bounded
relocatable-PIE planner. It supports their four load segments and modern
metadata while enforcing load-bias alignment, W^X, mapped-page separation,
interpreter identity, image page quotas, and non-overlapping main/interpreter
address ranges. Invalid bases, interpreter substitutions, and overlapping
layouts are rejected.

The kernel now maps the hundreds of BusyBox and musl pages through a dedicated,
scrubbed runtime extent, builds the Linux initial stack and auxiliary vector,
starts the unmodified musl interpreter in ring 3, permits musl to establish its
TLS base and RELRO protections, and connects standard input/output to the
serial console. The automated transcript enters `/bin/sh`, executes a shell
builtin, and exits cleanly back to the controller. Alpine is never reported as
running through the synthetic C2 `/sbin/init` fixture.

This is intentionally the first execution slice, not the completed C3 gate.
Rootfs-backed file syscalls and external BusyBox applets, process creation,
detach/reattach with retained logs, runtime registry pull, and container
networking remain before C3 is complete.

## Required runtime interaction

The target operator flow is explicit:

```text
container new alpine
container set alpine image=alpine:latest init=/bin/sh
container start alpine
```

The controller accepts `alpine`, `alpine:latest`, `alpine:3.24.2`, and their
fully qualified Docker Hub forms. For this embedded profile it resolves those
aliases to `docker.io/library/alpine:3.24.2`, which is what `container list`
reports. The image remains bound to the verified manifest digest shown above;
arbitrary runtime registry resolution is still a later C3 step.

In the completed C3 path, start will automatically pull a missing image.
Currently `make run` fetches and embeds the verified profile before boot.
Start-and-attach and later attach will both connect to the container console;
`Ctrl-]` will return to `ginux>` without stopping the container. A bounded boot
log will remain available after detach.

Container records, cached image objects, writable overlays, and temporary data
remain boot-local in C3. Persistent image/configuration storage is a later
checkpoint. A future configurable pre-init policy may run declarative YAML
scriptlets before `/sbin/init` for systemd images; it is not an implicit Alpine
default and is not part of the shell checkpoint.
