# C3 Verification: Rocky systemd Early Boot

**Implementation status:** In progress.

## Pinned image input

C3 uses Rocky Linux's systemd-capable UBI init image for x86-64. The profile
pins the architecture-specific manifest digest rather than a mutable tag:

```text
rockylinux/rockylinux@sha256:2ce9a2d1a810a47c72a86f79de7d54667bd922d2cec9880647ff6a9023f6fe8c
platform: linux/amd64
init: /sbin/init
```

Prepare and validate it on macOS or Linux with Docker:

```sh
make rocky-image
make rocky-image-check
```

The first command downloads the exact manifest, verifies its platform and
configured command, exports its root filesystem to
`build/rocky-10-system-v0/rootfs.tar`, and records local artifact metadata in
`build/rocky-10-system-v0/image.tsv`. The second command is offline and checks
the exported filesystem, metadata, digest, dynamic loader, and systemd binary.

## Current compatibility boundary

The pinned root filesystem is about 254 MiB unpacked. The current C2 measured
root is a deliberately bounded 192 KiB embedded newc fixture with at most 64
indexed entries. Rocky therefore cannot be substituted into that fixture.
C3 uses a separately authenticated, content-addressed container-image object
in a bounded RAM-backed tmpfs cache. `container start NAME` checks that cache
and automatically pulls the configured image when it is absent. The pull is
streamed through bounded staging, every descriptor and layer digest is
verified, and only a complete immutable image is published. Partial or failed
pulls never become visible.

The embedded C2 fixture remains the default `make build` input until that
tmpfs-backed image path is complete. This keeps existing verified boot and
failure-containment behavior intact while C3 is developed.

The original `/tmp/ginux-ready` implementation has been generalized into a
generation-safe, quota-enforced multi-object RAM store with dynamically
allocated owned pages, cross-page I/O, hidden staging, atomic publish, abort,
frame scrubbing, complete lease recovery, and stale-handle rejection. The
Linux syscall view still exposes only that fixture file. The QEMU profile
defaults to 1 GiB because the pinned root is about 254 MiB unpacked. The
current page-backed implementation deliberately caps each proof object at four
pages and the store at eight pages. The next storage step must remove those
proof-scale limits by making allocator and object metadata scale to the pinned
image while preserving the same transitions and avoiding redundant whole-image
copies. Quota or allocation exhaustion must fail the pull or start operation
without affecting the controller or running containers.

Container records, cached images, writable overlays, and temporary files are
intentionally lost on host reboot in C3. Persistent storage remains a C5 gate:
the controller will initialize a selected local volume, copy and verify state,
stage it as pending, and reboot to activate it. The following boot validates
the selection and volume before use; mutable volume contents cannot replace
the authenticated kernel, embedded controller, or sealed authority envelope.

## Required runtime interaction

Before the controller can pull the pinned image itself, the control domain
needs operator-configurable static or DHCP networking plus routes, DNS, TCP,
and TLS. Container configuration separately defines each container interface
as static or DHCP; it never inherits the control-domain network implicitly.

Starting with attach enabled and attaching later must both connect the
terminal to the container's console. `Ctrl-]` detaches without stopping the
container and returns to the `ginux>` control prompt. A bounded retained boot
log remains available after detach so early systemd failures can be inspected.
