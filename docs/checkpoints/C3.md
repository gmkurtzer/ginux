# C3 Verification: Alpine Shell Container

**Implementation status:** In progress.

## Pinned image input

C3 starts with the unmodified Alpine 3.24.2 x86-64 image and its configured
`/bin/sh`. The profile pins the architecture-specific manifest, config, layer,
and expanded rootfs digests; no container receives an implicit image.

```text
alpine@sha256:d56c381f961d307a21b3ca004cf1e3910f106644aefb1f43e654c8a56c4fd395
platform: linux/amd64
init: /bin/sh
```

Prepare, verify, build, and boot it on macOS or Linux with Docker and QEMU:

```sh
make alpine-image
make alpine-image-check
make build-alpine
make run-alpine
```

`make test-alpine` performs the non-interactive QEMU ingestion gate. The
ordinary `make build` remains independent of Docker and does not silently
select an image.

## Completed ingestion boundary

The preparation path pulls the exact linux/amd64 manifest, retains the OCI
layout, verifies the manifest/config/layer descriptors, expands the layer, and
verifies its OCI diff ID. The Alpine-enabled boot carries that verified rootfs
as a read-only boot object. The kernel independently verifies the full rootfs
SHA-256, validates bounded tar structure and paths, resolves
`/bin/sh -> /bin/busybox`, and validates the BusyBox and musl ELF inputs.

This is a temporary local-input path for execution development, not the final
runtime registry pull. The final path resolves the configured reference over
control-domain DNS/TCP/TLS, streams objects through transactional boot-local
storage, verifies each digest, and atomically publishes the image. Failed or
partial pulls never become visible.

## Current execution boundary

The C2 Linux loader is intentionally a proof loader: it accepts at most three
load segments and a small fixed number of pages. Alpine BusyBox and its musl
loader each use four load segments and together require hundreds of pages.
Consequently the rootfs is now ingested and inspected, but `/bin/sh` is not yet
executed. The next implementation step is a quota-bound general ELF mapper
with scalable page ownership, followed by serial-console input and detach.
Alpine must never be reported as running through the synthetic C2 `/sbin/init`
fixture.

## Required runtime interaction

The target operator flow is explicit:

```text
container new alpine
container set alpine image=alpine@sha256:d56c381f961d307a21b3ca004cf1e3910f106644aefb1f43e654c8a56c4fd395 init=/bin/sh
container start alpine
```

Start automatically pulls a missing image. Start-and-attach and later attach
both connect to the container console; `Ctrl-]` returns to `ginux>` without
stopping the container. A bounded boot log remains available after detach.

Container records, cached image objects, writable overlays, and temporary data
remain boot-local in C3. Persistent image/configuration storage is a later
checkpoint. A future configurable pre-init policy may run declarative YAML
scriptlets before `/sbin/init` for systemd images; it is not an implicit Alpine
default and is not part of the shell checkpoint.
