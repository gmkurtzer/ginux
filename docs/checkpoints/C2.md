# C2 Verification: Configured Container Autostart

**Implementation status:** Complete; awaiting human verification.

## Capability

The signed measured-root profile authenticates one bounded entry:

```text
container	default	autostart	/sbin/init	cpu=1	memory_mib=128
```

The kernel validates the same exact record before starting the configured
fixture. Its Linux `/sbin/init` runs as PID 1 in its container process view and
appears as PID 100 in the host `/proc` view. The ring-3 controller remains a
separate host process with delegated inspection and lifecycle authority.

The controller adds these commands:

- `container status default`
- `container stop default`
- `container start default`
- `container restart default`
- `container fail default`

Stop and injected-failure transitions terminate and clean up the running init
before returning control. Start and restart create a fresh measured init
instance. The injected failure is a controlled lifecycle failure transition,
not an arbitrary CPU fault.

## Automated verification

```sh
make test-c2
```

The gate verifies authenticated autostart, readiness, host PID visibility,
stop, restart, contained failure, recovery, clean shutdown, and rejection of a
modified container resource grant.

## Human verification on macOS

```sh
make doctor
make run
```

At `ginux>`, run `ps`, `ls /proc`, and each `container` command above. Confirm
that PID 100 is visible only while `default` is running, failure does not panic
the host, and `container start default` recovers it. Finish with `shutdown`.

## Boundary of this checkpoint

This is the pinned minimal Linux fixture, not Rocky Linux or systemd. It proves
the configured lifecycle and authority boundary. General container domains,
per-container networking (including static and DHCP configuration), and the
Rocky compatibility work remain subsequent checkpoints.
