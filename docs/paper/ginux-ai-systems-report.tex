\title{\textbf{Ginux: AI Can Build a Kernel, but It Cannot Manufacture an Ecosystem}}
\author{Gregory M. Kurtzer}
\date{Draft technical report --- October 2026}

\begin{document}
\maketitle

\begin{abstract}
This research asked two questions: can an AI coding agent, under expert
direction, build a new kernel capable of running an existing Linux userspace;
and can a kernel-native domain serve as a useful isolation and resource-policy
boundary above individual processes? In eleven days, the experiment produced
an independent, Rust-first kernel that boots through UEFI, runs a controller
outside ring~0, ingests OCI images, executes an unmodified Alpine userspace,
and launches Rocky Linux 10 systemd as PID~1. It also produced kernel-owned
domains with distinct identities, resources, process trees, filesystems, and
scheduling policy. The evaluated artifact contains roughly 139,000 retained,
non-generated lines of implementation and test code across 1,037 commits.

The result is evidence of technical feasibility, not production readiness or
complete Linux compatibility. This report describes the artifact, a reusable
expert-directed development method based on written architecture and
executable milestone gates, and the limits exposed by the experiment. AI can
reproduce a surprising amount of complex systems software at low cost. It
cannot manufacture decades of compatibility, standards, hardware enablement,
community trust, vendor relationships, or operational ownership on the same
schedule.
\end{abstract}

\section{AI Built a Linux-Compatible Kernel. It Did Not Build Linux}

The experiment began with an ambitious research question: could an AI agent
build a kernel capable of running an existing Linux userspace? The answer,
within a bounded research profile, is yes. \project{} boots from firmware under QEMU,
provides its own memory manager, scheduler, process model, ELF loader, virtual
filesystems, networking, IPC, device paths, and Linux syscall translation, and
runs real Alpine and Rocky Linux components.

\project{} contains no Linux kernel. Linux is the userspace compatibility
target. The distinction is visible in \texttt{uname}: a Linux-personality
domain reports \project{}, rather than claiming that the kernel itself is
Linux. ``Linux-compatible'' here means that selected unmodified Linux programs
observe enough of their expected ABI to run. It does not mean complete Linux
behavior.

The name is a deliberate joke in the same family as Linux. ``Linux'' combines
Linus and Unix; ``Ginux'' riffs on Linux, GPT, and Greg. For purposes of
authorial restraint, the ``G'' is treated as GPT.

The scope must be explicit: this was never an attempt to compete with Linux. The Linux
kernel community has spent decades doing the difficult work of supporting
hardware, preserving interfaces, reviewing security-sensitive changes, and
maintaining software people actually depend on. Eleven days of enthusiastic
AI-assisted kernel development does not put \project{} in that category.

The frozen artifact is commit \evaluatedcommit{}, dated October 20, 2026.

\section{What Ginux Is}

\subsection{A simplified boot architecture}

UEFI changes the assumptions inherited from the BIOS era. Firmware loads a
PE32+ application into memory, including all of its sections, through
\texttt{LoadImage()}~\cite{uefi211}. It does not require an operating system to
fit inside a 512-byte boot sector or walk through a chain of progressively
larger bootstrap loaders. Firmware quality, available memory, filesystem
support, and PE/COFF representation remain practical constraints; the payload
is not literally unlimited.

Ginux uses that freedom to boot one \texttt{GINUX.EFI} image containing its
Rust-first kernel, required x86-64 assembly, embedded controller payload,
component catalog, and recovery metadata. There is no required host
distribution, separate bootloader, or separate initramfs. After leaving UEFI
boot services, the kernel establishes paging, interrupts, protection,
scheduling, capabilities, storage, and networking, then launches the embedded
controller as a normal ring-3 process. Embedding the controller in the image
does not place it in kernel space.

This packaging simplified an experiment that otherwise would have needed to
coordinate a bootloader, kernel image, initramfs, host root filesystem, and
userspace versioning. It also supported the project's immutability model: the
kernel, controller, initial authority, and boot-required components can be
measured as one artifact before execution. A production system would still
need a mature update, rollback, signing, recovery, and firmware-compatibility
story.

\subsection{Implementation anatomy}

Ring~0 contains the mechanisms that must enforce a system-wide invariant:
page tables and address spaces, scheduling, capabilities, IPC, interrupt and
timer handling, domain ownership, the Linux personality boundary, and the
trusted side of device and DMA control. The x86-64 implementation does not use
rings~1 or~2. Ring~3 contains the controller, Linux workloads, and isolated
native services. Consequently, embedding a program in \texttt{GINUX.EFI}
describes how its bytes arrive, not the privilege at which they execute.

The controller is a freestanding, statically linked Rust program using the
Linux ABI for ordinary process behavior and a versioned device/\texttt{ioctl}
interface for Ginux management. It parses commands, maintains domain and
network configuration, starts and observes workloads, and manages persistent
configuration and the OCI cache. It is the initial administrative authority,
but it cannot rewrite the kernel or manufacture rights outside the sealed boot
authority envelope.

Device support is deliberately split. The kernel discovers PCI devices and
retains interrupt-controller, MSI-X, IOMMU, and capability enforcement. The
prototype includes virtio block and network paths and demonstrates measured
Rust driver/protocol services in separate ring-3 domains with bounded MMIO,
DMA, queue, and packet authority. Capabilities and resources are tagged with a
domain generation so a crashed service can be quiesced, revoked, and replaced
without treating its successor as the same security identity. This is a
demonstrated direction, not yet a general driver framework or hardware matrix.

The filesystem side is similarly purpose-built. Kernel VFS and mount behavior
present domain-local roots assembled from verified OCI layers, a writable
overlay, and selected \texttt{tmpfs}, \texttt{procfs}, and \texttt{devfs}
semantics. A host-owned block volume preserves controller configuration and a
content-addressed image cache. Immutable file pages are shared within a domain
and copied when made writable. Small assembly boundaries enter and leave UEFI,
install exception, interrupt, and syscall entries, switch privilege and
address-space state, and provide ABI probes; policy and most mechanisms remain
in Rust.

\subsection{Controller, domains, and personalities}

The controller configures the host and creates workload domains. It manages
domain lifecycle, images, resources, networks, persistent configuration, and
the local OCI cache through a versioned control interface. Host administration
therefore remains in userspace even though the controller arrives inside the
boot image.

A \emph{domain} is a native Ginux kernel object, not an OCI container or a
renamed Linux namespace. It owns or is granted address spaces, a process tree,
capabilities, IPC objects, filesystem and mount views, networks, devices,
limits, lifecycle, and failure policy. OCI supplies a domain's initial
filesystem; Ginux supplies its isolation and execution. A single domain can
look like a conventional computer, with systemd as PID~1 and a distribution
userspace above it. Multiple domains share one kernel while retaining separate
kernel-owned identities and resources.

Domains are also scheduling principals. The implemented CPU scheduler chooses
the highest ready domain service class and schedules processes within that
class. The architecture extends that model to independent CPU, memory,
storage-I/O, and network-I/O classes, allowing one domain to receive
latency-sensitive service while another scavenges spare capacity. Complete
cross-resource QoS enforcement remains future work. The experiment establishes
the architectural boundary and part of the scheduling model, not the final
policy system.

A \emph{personality} defines the userspace contract visible inside a domain:
executable format, syscalls, process and signal behavior, VFS semantics,
devices, terminals, clocks, networking, and namespace expectations. Linux
x86-64 is the only implemented personality. BSD is a plausible experiment
because it could reuse the same domain, memory, scheduling, and device
mechanisms, but no BSD ABI was built or tested. Linux namespaces may eventually
subdivide a Linux domain; they would remain inside the stronger outer domain
boundary.

Storage follows this separation. Domain roots may be assembled from
verified OCI layers and receive a boot-local writable overlay. Ginux also has
a persistent host-owned volume for controller configuration and a
content-addressed OCI layer cache, so a reboot need not redownload every image
or forget every domain. It currently provides selected tmpfs, overlay, procfs,
devfs, and persistent-volume behavior. It does not provide Linux's broad
filesystem ecosystem or production storage guarantees.

\subsection{POSIX surface, identities, and permissions}

Linux syscall-number coverage is not a measure of POSIX conformance. POSIX is
primarily a source and behavioral contract across libc, processes, files,
signals, terminals, clocks, synchronization, and IPC. The evaluated musl and
glibc userspaces exercise fork/exec/wait, path and descriptor operations,
pipes and FIFOs, signals, clocks, termios, sockets, futex-based threading, and
selected POSIX and System~V IPC. Coverage is partial: Ginux has not run a
complete POSIX conformance suite and makes no certification claim.

Each domain owns a sealed native capability table. A capability names one
kernel object and grants some combination of read, write, manage, and execute.
Initial authority comes only from the boot envelope; delegation can attenuate
but not expand it; handles are generation tagged, and root revocation removes
derived rights. Devices, DMA pages, queues, volumes, and management operations
can therefore be granted independently. A domain also owns its configured CPU
and memory budgets, address spaces, processes, IPC, filesystem/mount views,
networks, devices, lifecycle, and failure policy. CPU service classes are
scheduled today; complete memory and I/O contention enforcement is unfinished.

Inside that boundary, the Linux personality applies domain-local credentials
and permissions. The evaluated profile maps UID/GID~0 to kernel ID~100000 and
uses real/effective/saved IDs in signal, cross-process, and file-access checks.
The VFS implements mode, ownership, \texttt{umask}, and access operations used
by the package-manager path. The profile has one mapped identity, no Linux
capabilities, and denies many credential mutations. POSIX ACLs and permission
edge cases remain incomplete; no SELinux or other active Linux security module
enforces labels. Linux UID~0 cannot bypass the native capability table.

\subsection{Optimization and security hypotheses}

The architecture places authorization on the control path while permitting an
approved data path to use shared pages, hardware queues, batching, and direct
interrupt delivery. Domains are scheduling and accounting principals, so CPU
service class and, eventually, memory, storage, and network policy can be
applied above individual processes. The intended advantage is less duplicated
host machinery and fewer crossings on steady-state I/O, not an assumption that
new code is inherently faster.

There is one narrow performance result. On the Apple Silicon development host,
QEMU translated x86-64 execution reached the verified Rocky console in
4,081--4,083~ms from Linux init at the evaluated checkpoint; a rerun for this
revision measured 4,384~ms. Profiling had reduced the original 15,344~ms path
by removing a polling stall, quadratic frame scans, and eager duplication of
immutable root-filesystem pages. These are regression measurements under TCG,
not comparisons with Linux or evidence of native performance. The repository
defines a three-second KVM gate, but it still requires execution on an x86-64
Linux host. Broader CPU, memory, IPC, network, storage, and application
benchmarks remain necessary before publication of any competitive claim; the
method and limitations are recorded in the
\repolink{docs/PERFORMANCE.md}{performance record}.

The security hypothesis is that explicit capabilities, per-domain address
spaces, W\textasciicircum X mappings, immutable executable pages,
generation-safe revocation, and IOMMU-confined DMA reduce ambient authority
and contain component failure. The prototype exercises several positive and
negative paths, including stale-generation rejection and driver teardown.
It has not received an independent audit, side-channel analysis, formal
verification of the whole kernel, or adversarial production testing. These
mechanisms are reasons to investigate the design, not evidence that Ginux is
more secure than Linux.

\subsection{Implemented result and research boundary}

The prototype boots a unified x86-64 EFI image, runs its controller in ring~3,
acquires networking under QEMU, and pulls and caches OCI filesystems. It runs
Alpine musl/BusyBox and Rocky glibc programs, launches Rocky systemd through
\texttt{multi-user.target}, and retains independent process, address-space,
root, mount, and lifecycle state across multiple domains.

The ledger classifies all 375 Linux 6.12 x86-64 syscall numbers: 82 Complete,
245 Partial, and 48 Policy-denied. These counts provide coverage, not
completeness. Loader and process behavior, pseudo-filesystems, cgroups,
namespaces, IPv6, ioctl families, filesystems, and devices remain incomplete.
There is no GPU ecosystem, broad hardware support, stable third-party driver
ABI, independent security audit, native performance baseline, or general Linux
application guarantee.

Those omissions define the research boundary. The question was whether AI
could construct a kernel and carry a real Linux userspace across it, not
whether eleven days could replace decades of Linux engineering. Useful ideas,
including domains, may ultimately belong in established systems rather than a
Ginux deployment.

\subsection{Illustrative operator workflows}

The following condensed transcripts show the intended operator experience.
They use implemented controller commands but omit lengthy registry, systemd,
and timing output. They are illustrative pseudo-screenshots rather than raw
benchmark logs.

\begin{samepage}
\noindent\textbf{Example 1: boot a conventional Linux userspace.}\par\nopagebreak
\begin{quote}\small\hrule\vspace{4pt}
\begin{verbatim}
ginux> domain new rocky
rocky: created (image required)
ginux> domain set rocky image=rockylinux/rockylinux:10-ubi-init
ginux> domain set rocky init=/sbin/init memory-mib=2048
rocky: settings accepted; configured
ginux> domain start rocky --attach
ginux: OCI cache hit (2 layers)
ginux: starting Linux personality domain
systemd: Reached target Multi-User System.
Rocky Linux 10
rocky login:
\end{verbatim}
\vspace{2pt}\hrule
\end{quote}
\end{samepage}

This single-domain case selects a Linux userspace image and init process while
Ginux remains the kernel. The controller can also manage several domains
without treating any one workload as the host operating system.

\begin{samepage}
\noindent\textbf{Example 2: reuse content across several domains.}\par\nopagebreak
\begin{quote}\small\hrule\vspace{4pt}
\begin{verbatim}
ginux> domain new alpine-a
ginux> domain set alpine-a image=alpine:latest init=/bin/sh
alpine-a: settings accepted; configured
ginux> domain start alpine-a
ginux: OCI cache miss; pulling 1 layer
alpine-a: running (detached)
ginux> domain new alpine-b
ginux> domain set alpine-b image=alpine:latest init=/bin/sh
ginux> domain start alpine-b
ginux: OCI cache hit (1 layer)
alpine-b: running (detached)
ginux> domain list
NAME       STATE    PERSONALITY  INIT       NETWORK
rocky      running  linux        /sbin/init host(shared)
alpine-a   running  linux        /bin/sh    host(shared)

\end{verbatim}
\vspace{2pt}\hrule
\end{quote}
\end{samepage}

After reboot, the controller recovers the domain definitions and cached OCI
layers from the host-owned volume. Writable domain overlays remain boot-local
at the evaluated checkpoint, so configuration and image caching are persistent
without implying that every workload mutation is durable.

\section{Methods}

\subsection{From an idea to an executable plan}

The method began with questions rather than code. An initial concept was
interrogated through sustained question-and-answer with the agent: what belonged
in ring~0, what Linux compatibility meant, how domains differed from
namespaces, which privileges a controller required, and what observable result
would count as success. Corrections were incorporated into written artifacts
before they became implementation assumptions.

The first artifact was a collaborative architectural overview. The versioned
\repolink{ARCHITECTURE.md}{ARCHITECTURE.md} then developed the boot model,
kernel/userspace boundary, domains, authority, storage, devices, and acceptance
criteria in greater detail. The
\repolink{docs/LINUX-COMPATIBILITY.md}{Linux compatibility ledger} recorded
syscall and non-syscall behavior. The
\repolink{docs/NEXT-GOAL.md}{working goal},
\repolink{docs/USE-CASES.md}{use cases}, and
\repolink{docs/decisions/0001-native-domains-and-authority.md}{domain decision
record} kept both plan and rationale outside the chat transcript. These files
provided durable state for a long-running agent session and made architectural
drift visible.

\subsection{Staged construction}

Repository history and the project plans show six broad, overlapping stages:

\begin{enumerate}[leftmargin=*,label=\arabic*.]
\item \textbf{Boot and architecture.} Define the trust and domain model, build
  a unified x86-64 EFI image, exit UEFI boot services, establish a kernel stack,
  and inventory memory and ACPI state.
\item \textbf{Kernel mechanisms and hardware.} Add paging, frame ownership,
  exceptions, interrupts, the APIC timer, preemptive scheduling, capabilities,
  IPC, domain address spaces, PCI discovery, virtio paths, and IOMMU-mediated
  DMA confinement.
\item \textbf{Userspace control.} Enter ring~3, execute an embedded static
  controller as an ordinary userspace process, and expose versioned management
  operations for domains, networks, storage, and lifecycle.
\item \textbf{Linux execution.} Build an x86-64 ELF interpreter, PIE and dynamic
  loader support, process and signal semantics, virtual filesystems, terminals,
  sockets, and a growing Linux syscall surface.
\item \textbf{Distribution ingestion.} Add DHCP, DNS, TCP/TLS, OCI manifest and
  architecture selection, digest verification, layer unpacking, caching, and
  domain-local roots; then run Alpine and progressively larger Rocky Linux
  programs.
\item \textbf{Compatibility and system boot.} Turn discovered behavior into a
  Linux ABI test matrix, add persistence and multi-domain lifecycle tests, and
  use Rocky Linux systemd, service startup, and an interactive console as the
  compound integration gate.
\end{enumerate}

The order was intentionally progressive: firmware entry preceded hardware
control; a bounded ELF executable preceded a general Linux process; synthetic
ABI probes preceded Alpine; Alpine preceded glibc-based Rocky Linux; and Rocky
programs preceded systemd. Each stage converted its failures into requirements
for the next revision rather than treating a boot message as proof of
correctness.

\subsection{The closed-loop agent procedure}

Every milestone had an observable gate: boot the EFI image, enter a ring-3
controller, create a named domain, execute an Alpine shell, pull an OCI image
over the network, run Rocky binaries, launch systemd, and reach a console. The
agent received a goal and iterated until the acceptance behavior was observed.
The reusable loop was:

\begin{center}
\fbox{\parbox{0.91\linewidth}{
architecture $\rightarrow$ milestone $\rightarrow$ executable gate
$\rightarrow$ implementation $\rightarrow$ build and QEMU run
$\rightarrow$ failure analysis $\rightarrow$ revision $\rightarrow$ human
evaluation $\rightarrow$ signed commit.
}}
\end{center}

Codex selected implementations, edited the repository, compiled the system,
booted QEMU, read logs, wrote tests, updated documentation, profiled failures,
and continued to the next gate. It also drafted much of the documentation and
report prose, which received editorial review. Human direction supplied the
architecture, priorities, compatibility target, stopping decisions, and
skepticism about false success; it did not prescribe individual edits. The
agent was given outcomes and room to solve them, while executable gates
prevented console output alone from satisfying a milestone.

The tests became progressively less synthetic. Small probes established entry
paths and syscall mechanics. Alpine exposed filesystem, working-directory,
fork, and exec errors. Rocky exercised glibc, dynamic loading, and larger
mappings. systemd combined scheduling, epoll, signals, procfs, sockets,
mounts, credentials, timers, and console lifecycle. Interactive operator tests
found workflow failures that adjacent automated tests had missed. The result
was a productive, repeatable loop, not an autonomous proof of correctness. A
comparable project can apply the same procedure: refine the idea through
Q\&A, write progressively detailed architecture, externalize the plan, define
executable gates, permit bounded agent iteration, review the evidence, and
record both decisions and remaining gaps before advancing.

\section{Alternative: Starting with Linux}

A practical product effort would have had strong reasons to begin with Linux.
Namespaces, cgroups, KVM, device drivers, filesystems, security modules, and a
vast compatibility suite already exist. A Ginux-like controller could manage
an immutable Linux host, while a domain experiment could initially combine
those mechanisms and add scheduler, device, and resource-policy changes where
the existing abstractions proved insufficient. That route would have produced
broader hardware and application support much sooner.

It would also answer a different question. This experiment deliberately
removed Linux from the kernel side to test whether an expert-directed AI could
construct the machinery itself and discover a distinct outer isolation object.
Starting with Linux would shift the work from reimplementation toward
integration, hardening, measurement, and upstream-quality design. That may be
the more valuable implication: if AI can traverse the from-scratch path, an
expert can instead aim it at bounded improvements to a mature system, where
the ecosystem remains intact and the novel idea must survive existing review,
compatibility, and performance standards.

\section{Expertise Still Drives the Agent}

This result does not imply that domain expertise is optional. AI compressed
the time required to turn decisions into code. It did not supply all of the
decisions. Choosing a Linux userspace contract, distinguishing OCI
transport from runtime isolation, recognizing broken fork/exec behavior,
defining domain ownership, interpreting systemd failures, and rejecting false
success all required domain knowledge.

The project direction drew on experience from Caos Linux, CentOS, and Rocky
Linux; the Singularity/Apptainer container ecosystem; the Warewulf and Perceus
cluster-provisioning ecosystems; and production infrastructure operations
~\cite{rockyAbout2026,ciqKurtzer2026}. That background shaped the distinction
between OCI transport and runtime isolation, the controller workflow,
persistent image caching, domain boot semantics, provisioning requirements,
the acceptance gates, and the decision to stop. An inexperienced operator may
obtain a large codebase and convincing console output without recognizing that
the underlying semantics are wrong. In systems software, a plausible result
can be more dangerous than an obvious failure.

AI nevertheless lowers the barrier for junior engineers to contribute. They
can explore unfamiliar code, generate tests, compare interfaces, and implement
bounded work at a speed that previously required much more experience. The
remaining gap is judgment: knowing which abstraction to choose, which result
to distrust, what compatibility means, and when a local success creates a
system-wide liability. Senior engineers who adopt an AI-first workflow have
the strongest combination today because they can pair generation speed with a
well-developed model of how the system should behave.

This also argues for better controls. Architecture must be written down. Gates
must exercise operator workflows rather than convenient markers. Compatibility
claims need external references and differential tests. Security review should
not be performed solely by the same agent that wrote the code. AI expands who
can build; it does not remove responsibility for what gets built.

\section{Code Is Not the Moat}

The author-estimated API cost of Ginux was \estimatedcost---about USD~7.71 per
commit or USD~0.058 per retained, non-generated implementation/test line.
Those ratios are intentionally crude. A line can be generated cheaply while
its compatibility burden lasts for years. The experiment measured the cost of
producing a prototype, not the cost of making it trustworthy, integrating it
with an industry, or maintaining it.

AI is already applying similar pressure to application software. In October
2026, ArtCraft published early Rust implementations modeled on seven Adobe
Creative Cloud applications, developed with heavy use of Claude
~\cite{artcraft2026}. Independent hands-on testing found recognizable tools
and striking development speed, along with missing features and basic failures
that prevented production replacement~\cite{creativebloqArtcraft2026}. That is
the Ginux lesson at application scale: reproducing a visible capability has
become dramatically cheaper; reproducing its full behavior, integrations,
workflows, support, and trust has not.

The resulting replication pressure is likely to be strongest above middleware
and orchestration, where organizations can replace or customize applications
without persuading an entire hardware and software ecosystem to move with
them. Foundational software can also be reimplemented---Ginux proves the
point---but enterprise infrastructure is selected through standards,
interfaces, certification, hardware enablement, community continuity, and a
commercial support matrix. A technically interesting replacement that nobody
else supports is usually a liability.

Linux is the clearest example. Its value is not reducible to the source needed
to boot a shell. It includes stable expectations across processors,
filesystems, devices, hypervisors, distributions, security teams, silicon
vendors, cloud providers, and application developers. Ginux has none of that.
It has no vendor-supported GPU stack, almost no physical-hardware matrix, no
broad filesystem support, no standards body, and no community obligated to
keep yesterday's programs working tomorrow. AI may help build each missing
piece, but it cannot unilaterally make independent organizations adopt the
same contracts.

\subsection{AI accelerates both sides of open-source security}

The following episode is external context, not evidence produced by the Ginux
experiment. It illustrates why the operational consequences of AI-assisted
software work extend well beyond the team generating code.

The capability that generates new software can also audit old software at a
scale human teams could not previously sustain. In 2026, AI-assisted research
helped expose critical PHP flaws capable of unauthenticated remote code
execution. The underlying out-of-memory problem had been recognized in 2024,
but its full impact emerged through later reports involving Calif, OpenAI, and
Wiz~\cite{phpStaleState2026,openaiPatchPlanet2026,phpFoundation2026}. AWS later
reported an exploitation attempt four days before public disclosure
~\cite{awsPhp2026}. Defenders cannot assume that they discover the bug first.

Discovery was only the beginning. The PHP Foundation reports that its team
handled more than 100 invalid, duplicate, or irreproducible submissions while
people validated every finding and wrote every patch. The Foundation also says
Chainguard published fixed images more than six hours before the coordinated
release, making the change available for comparison while much of the
ecosystem was still preparing~\cite{phpFoundation2026}. Chainguard's chief
executive said the decision responded to reports of active exploitation
~\cite{techtargetPhp2026}. The decision to publish ahead of the coordinated
release is not part of this research and is not adjudicated here. It is
nevertheless an important data point: faster discovery and evidence of
exploitation compress disclosure and deployment windows for maintainers,
distributors, vendors, and operators.

Open source already contains vulnerabilities missed during human review. AI
will find more of them, and attackers can use it too. The near
term may therefore get worse before it gets better: report volume rises,
maintainers must separate real exploits from plausible noise, disclosure
windows shrink, and organizations must deploy fixes faster. Much of the pain
falls on operations and security teams at large organizations: they must map
affected packages to fleets, evaluate provenance, prioritize exposure, test
updates, and safely deploy them under an increasingly compressed deadline.

A categorical prohibition on AI-assisted open-source contributions is the
wrong response to that pressure. Projects should accept and actively encourage
AI-assisted reports, tests, and fixes, particularly when AI is also increasing
the rate at which defects are found. The standard should attach to the
evidence, not the tool: reproducible reports, focused patches, regression
tests, provenance, accountable review, coordinated disclosure, and the same or
higher bar for correctness. Evidence-free automated submissions and automatic
merging remain harmful. Excluding a valid fix solely because AI participated
would discard useful defensive capacity precisely when maintainers and
operators need it most.

\section{Conclusion}

Ginux demonstrates something that would have sounded absurd not long ago: an
expert can direct an AI coding agent to build a new kernel, implement enough of
the Linux userspace contract to run real distributions, and explore a new
kernel-native domain architecture in days. The result deserves genuine
excitement.

It also deserves restraint. Ginux is a research artifact, not a production
kernel. It should not run production infrastructure, and it does not threaten
Linux. If domains or any
other idea prove useful, success may mean contributing the idea to established
systems rather than asking the world to adopt another kernel.

AI can build code. Ginux shows that the boundary now reaches deep systems
software. The durable questions are whether that code honors existing
contracts, whether independent organizations will support it, whether people
can secure and maintain it, and who remains accountable after the agent stops.
That ecosystem is the moat, and no prompt can conjure it overnight.
