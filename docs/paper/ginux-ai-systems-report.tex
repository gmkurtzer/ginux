\title{\textbf{Ginux: AI Can Build a Kernel, but It Cannot Manufacture an Ecosystem}}
\author{Gregory M. Kurtzer}
\date{Draft technical report --- October 2026}

\begin{document}
\maketitle

\begin{abstract}
An AI coding agent built a new Linux-compatible kernel. It boots directly
through UEFI, runs a controller outside ring~0, ingests OCI images, executes an
unmodified Alpine userspace, and launches Rocky Linux 10 systemd as PID~1. The
kernel is not Linux: it is an independent, Rust-first implementation of the
kernel mechanisms and Linux userspace contract exercised by those workloads.
In eleven days, the project reached roughly 139,000 retained, non-generated
lines of implementation and test code across 1,037 commits.

This report describes what was built, the expert-directed agent loop that
produced it, and the limits of the result. \project{} is a research prototype,
not a production kernel or a proposed replacement for Linux. That distinction
is the main finding. AI can reproduce a surprising amount of complex software
at low cost. It cannot generate decades of compatibility, standards, hardware
enablement, community trust, vendor relationships, or operational ownership on
the same schedule.
\end{abstract}

\section{AI Built a Linux-Compatible Kernel. It Did Not Build Linux}

We began with a deliberately unreasonable question: could an AI agent build a
kernel capable of running an existing Linux userspace? The answer, within a
bounded research profile, is yes. \project{} boots from firmware under QEMU,
provides its own memory manager, scheduler, process model, ELF loader, virtual
filesystems, networking, IPC, device paths, and Linux syscall translation, and
runs real Alpine and Rocky Linux components.

\project{} contains no Linux kernel. Linux is the userspace compatibility
target. The distinction is visible in \texttt{uname}: a Linux-personality
domain reports \project{}, rather than claiming that the kernel itself is
Linux. ``Linux-compatible'' here means that selected unmodified Linux programs
observe enough of their expected ABI to run. It does not mean complete Linux
behavior.

The name is a small joke in the same family as Linux. ``Linux'' combines Linus
and Unix; ``Ginux'' riffs on Linux, GPT, and Greg. We will say the ``G'' stands
for GPT so the author's head does not get any bigger.

Eyes wide open: this was never an attempt to compete with Linux. The Linux
kernel community has spent decades doing the difficult work of supporting
hardware, preserving interfaces, reviewing security-sensitive changes, and
maintaining software people actually depend on. Eleven days of enthusiastic
AI-assisted kernel hacking does not put \project{} in that category. Kernel
maintainers may safely postpone their panic.

\section{What Ginux Is}

\subsection{A simplified boot architecture}

UEFI changes the assumptions inherited from the BIOS era. Firmware loads a
PE32+ application into memory, including all of its sections, through
\texttt{LoadImage()}~\cite{uefi211}. It does not require an operating system to
fit inside a 512-byte boot sector or walk through a chain of progressively
larger bootstrap loaders. Firmware quality, available memory, filesystem
support, and PE/COFF representation remain practical constraints; the payload
is not literally unlimited.

Ginux uses that freedom to boot one \texttt{GINUX.EFI} image containing its
Rust-first kernel, required x86-64 assembly, embedded controller payload,
component catalog, and recovery metadata. There is no required host
distribution, separate bootloader, or separate initramfs. After leaving UEFI
boot services, the kernel establishes paging, interrupts, protection,
scheduling, capabilities, storage, and networking, then launches the embedded
controller as a normal ring-3 process. Embedding the controller in the image
does not place it in kernel space.

This packaging simplified an experiment that otherwise would have needed to
coordinate a bootloader, kernel image, initramfs, host root filesystem, and
userspace versioning. It also supported the project's immutability model: the
kernel, controller, initial authority, and boot-required components can be
measured as one artifact before execution. A production system would still
need a mature update, rollback, signing, recovery, and firmware-compatibility
story.

\subsection{Controller, domains, and personalities}

The controller configures the host and creates workload domains. It manages
domain lifecycle, images, resources, networks, persistent configuration, and
the local OCI cache through a versioned control interface. Host administration
therefore remains in userspace even though the controller arrives inside the
boot image.

A \emph{domain} is a native Ginux kernel object, not an OCI container or a
renamed Linux namespace. It owns or is granted address spaces, a process tree,
capabilities, IPC objects, filesystem and mount views, networks, devices,
limits, lifecycle, and failure policy. OCI supplies a domain's initial
filesystem; Ginux supplies its isolation and execution. A single domain can
look like a conventional computer, with systemd as PID~1 and a distribution
userspace above it. Multiple domains share one kernel while retaining separate
kernel-owned identities and resources.

Domains are also scheduling principals. The implemented CPU scheduler chooses
the highest ready domain service class and schedules processes within that
class. The architecture extends that model to independent CPU, memory,
storage-I/O, and network-I/O classes, allowing one domain to receive
latency-sensitive service while another scavenges spare capacity. Complete
cross-resource QoS enforcement remains future work. The experiment establishes
the architectural boundary and part of the scheduling model, not the final
policy system.

A \emph{personality} defines the userspace contract visible inside a domain:
executable format, syscalls, process and signal behavior, VFS semantics,
devices, terminals, clocks, networking, and namespace expectations. Linux
x86-64 is the only implemented personality. BSD is a plausible experiment
because it could reuse the same domain, memory, scheduling, and device
mechanisms, but no BSD ABI was built or tested. Linux namespaces may eventually
subdivide a Linux domain; they would remain inside the stronger outer domain
boundary.

Storage follows this separation. Domain roots may be assembled from
verified OCI layers and receive a boot-local writable overlay. Ginux also has
a persistent host-owned volume for controller configuration and a
content-addressed OCI layer cache, so a reboot need not redownload every image
or forget every domain. It currently provides selected tmpfs, overlay, procfs,
devfs, and persistent-volume behavior. It does not provide Linux's broad
filesystem ecosystem or production storage guarantees.

\subsection{Implemented result and research boundary}

The current prototype boots a unified x86-64 EFI image; runs its static
Linux-ABI controller in ring~3; acquires networking under QEMU; pulls,
verifies, caches, and publishes OCI filesystems; runs Alpine musl/BusyBox and
Rocky glibc programs; and launches Rocky Linux 10 UBI systemd as domain PID~1
through \texttt{multi-user.target}. Multiple domains retain independent
process, address-space, root, mount, and lifecycle state. Controller commands
can start, stop, inspect, attach to, and execute a process inside a running
domain.

The compatibility ledger covers all 375 Linux 6.12 x86-64 syscall numbers,
classifying 82 Complete, 245 Partial, and 48 Policy-denied. Coverage is not
completeness. Loader behavior, process semantics, procfs, sysfs, cgroups,
namespaces, IPv6, ioctl families, filesystems, and devices remain incomplete.
Hardware support is limited to what the experiment implemented and exercised,
mostly through QEMU. There is no GPU ecosystem, broad physical-device support,
stable third-party driver ABI, independent security audit, native-hardware
performance baseline, or general assurance that Linux applications behave
correctly.

Those omissions do not spoil the experiment; they define it. The question was
whether AI could construct a new kernel and carry a real Linux userspace across
the boundary. It was not whether eleven days of research could replace thirty
years of Linux engineering. Features that prove useful---perhaps the domain
model itself---may be more valuable as ideas to explore in Linux or other
established systems than as reasons to deploy Ginux.

\section{How We Built It}

The work began as collaborative architecture, not code generation. The
versioned \repolink{ARCHITECTURE.md}{ARCHITECTURE.md} defined the boot model,
kernel/userspace boundary, domains, authority, storage, devices, and acceptance
criteria. The \repolink{docs/LINUX-COMPATIBILITY.md}{Linux compatibility
ledger} recorded syscall and non-syscall behavior. The
\repolink{docs/NEXT-GOAL.md}{working goal},
\repolink{docs/USE-CASES.md}{use cases}, and
\repolink{docs/decisions/0001-native-domains-and-authority.md}{domain decision
record} kept the plan outside the chat transcript.

From those documents we created milestones with observable gates: boot the EFI
image, enter a ring-3 controller, create a named domain, execute an Alpine
shell, pull an OCI image over the network, run Rocky binaries, launch systemd,
and reach a console. The agent received a goal and iterated until each gate met
its acceptance behavior. The loop was:

\begin{center}
\fbox{\parbox{0.91\linewidth}{
architecture $\rightarrow$ milestone $\rightarrow$ executable gate
$\rightarrow$ implementation $\rightarrow$ build and QEMU run
$\rightarrow$ failure analysis $\rightarrow$ revision $\rightarrow$ human
evaluation $\rightarrow$ signed commit.
}}
\end{center}

Codex selected implementations, edited the repository, compiled the system,
booted QEMU, read logs, wrote tests, updated documentation, profiled failures,
and continued to the next gate. It also drafted much of the documentation and
report prose, which the author reviewed and revised. The human role was
direction and judgment, not dictating individual edits. This matters: the agent
was given outcomes and room to solve them, but the plan, architecture,
compatibility target, and definition of acceptable behavior came from someone
who understood Linux and operating-system design.

The tests became progressively less synthetic. Small probes established entry
paths and syscall mechanics. Alpine exposed filesystem, working-directory,
fork, and exec errors. Rocky exercised glibc, dynamic loading, and larger
mappings. systemd combined scheduling, epoll, signals, procfs, sockets,
mounts, credentials, timers, and console lifecycle. Human interactive tests
found workflow failures that adjacent automated tests had missed. The result
was a productive loop, not an autonomous proof of correctness.

\section{Expertise Still Drives the Agent}

This result should not be read as ``anyone can ask for a kernel before lunch.''
AI compressed the time required to turn decisions into code. It did not supply
all of the decisions. Choosing a Linux userspace contract, distinguishing OCI
transport from runtime isolation, recognizing broken fork/exec behavior,
defining domain ownership, interpreting systemd failures, and rejecting false
success all required domain knowledge.

The author brought experience from Caos Linux, CentOS, and Rocky Linux, as well
as operating production software infrastructure
~\cite{rockyAbout2026,ciqKurtzer2026}. That experience changed the prompts, the
architecture, the acceptance gates, and the decision to stop. An inexperienced
operator may obtain a large codebase and convincing console output without
recognizing that the underlying semantics are wrong. In systems software, a
plausible result can be more dangerous than an obvious failure.

AI nevertheless lowers the barrier for junior engineers to contribute. They
can explore unfamiliar code, generate tests, compare interfaces, and implement
bounded work at a speed that previously required much more experience. The
remaining gap is judgment: knowing which abstraction to choose, which result
to distrust, what compatibility means, and when a local success creates a
system-wide liability. Senior engineers who adopt an AI-first workflow have
the strongest combination today because they can pair generation speed with a
well-developed model of how the system should behave.

This also argues for better controls. Architecture must be written down. Gates
must exercise operator workflows rather than convenient markers. Compatibility
claims need external references and differential tests. Security review should
not be performed solely by the same agent that wrote the code. AI expands who
can build; it does not remove responsibility for what gets built.

\section{Code Is Not the Moat}

The author-estimated API cost of Ginux was \estimatedcost---about USD~7.71 per
commit or USD~0.058 per retained, non-generated implementation/test line.
Those ratios are intentionally crude. A line can be generated cheaply while
its compatibility burden lasts for years. The experiment measured the cost of
producing a prototype, not the cost of making it trustworthy, integrating it
with an industry, or maintaining it.

AI is already applying similar pressure to application software. In October
2026, ArtCraft published early Rust implementations modeled on seven Adobe
Creative Cloud applications, developed with heavy use of Claude
~\cite{artcraft2026}. Independent hands-on testing found recognizable tools
and striking development speed, along with missing features and basic failures
that prevented production replacement~\cite{creativebloqArtcraft2026}. That is
the Ginux lesson at application scale: reproducing a visible capability has
become dramatically cheaper; reproducing its full behavior, integrations,
workflows, support, and trust has not.

The resulting replication pressure is likely to be strongest above middleware
and orchestration, where organizations can replace or customize applications
without persuading an entire hardware and software ecosystem to move with
them. Foundational software can also be reimplemented---Ginux proves the
point---but enterprise infrastructure is selected through standards,
interfaces, certification, hardware enablement, community continuity, and a
commercial support matrix. A technically interesting replacement that nobody
else supports is usually a liability.

Linux is the clearest example. Its value is not reducible to the source needed
to boot a shell. It includes stable expectations across processors,
filesystems, devices, hypervisors, distributions, security teams, silicon
vendors, cloud providers, and application developers. Ginux has none of that.
It has no vendor-supported GPU stack, almost no physical-hardware matrix, no
broad filesystem support, no standards body, and no community obligated to
keep yesterday's programs working tomorrow. AI may help build each missing
piece, but it cannot unilaterally make independent organizations adopt the
same contracts.

\subsection{AI accelerates both sides of open-source security}

The capability that generates new software can also audit old software at a
scale human teams could not previously sustain. In 2026, AI-assisted research
helped expose critical PHP flaws capable of unauthenticated remote code
execution. The underlying out-of-memory problem had been recognized in 2024,
but its full impact emerged through later reports involving Calif, OpenAI, and
Wiz~\cite{phpStaleState2026,openaiPatchPlanet2026,phpFoundation2026}. AWS later
reported an exploitation attempt four days before public disclosure
~\cite{awsPhp2026}. We cannot assume defenders always discover the bug first.

Discovery was only the beginning. The PHP Foundation reports that its team
handled more than 100 invalid, duplicate, or irreproducible submissions while
people validated every finding and wrote every patch. The Foundation also says
Chainguard published fixed images more than six hours before the coordinated
release, making the change available for comparison while much of the
ecosystem was still preparing~\cite{phpFoundation2026}. Chainguard's chief
executive said the decision responded to reports of active exploitation
~\cite{techtargetPhp2026}. Whatever judgment one makes about that decision,
the episode shows that security depends on trusted
coordination among maintainers, researchers, distributors, vendors, and
operators. Faster vulnerability discovery compresses the time available for
all of them.

Open source already contains vulnerabilities missed during human review. AI
will find more of them, and attackers can use it too. The near
term may therefore get worse before it gets better: report volume rises,
maintainers must separate real exploits from plausible noise, disclosure
windows shrink, and organizations must deploy fixes faster. Code generation
does not solve this coordination problem. It makes durable maintainership,
funded security work, reproducible validation, package provenance, rapid
patching, and trusted distribution more important.

\section{Conclusion}

Ginux demonstrates something that would have sounded absurd not long ago: an
expert can direct an AI coding agent to build a new kernel, implement enough of
the Linux userspace contract to run real distributions, and explore a new
kernel-native domain architecture in days. The result deserves genuine
excitement.

It also deserves restraint. Ginux is a research artifact with an excellent
demo and a very long list of ways to ruin someone's weekend. It should not run
production infrastructure, and it does not threaten Linux. If domains or any
other idea prove useful, success may mean contributing the idea to established
systems rather than asking the world to adopt another kernel.

AI can build code. Ginux shows that the boundary now reaches deep systems
software. The durable questions are whether that code honors existing
contracts, whether independent organizations will support it, whether people
can secure and maintain it, and who remains accountable after the agent stops.
That ecosystem is the moat, and no prompt can conjure it overnight.
