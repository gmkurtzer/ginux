\title{\textbf{Ginux: Methods and Outcomes of Building a Linux Userspace-Compatible Kernel with Expert-Directed AI}}
\author{Gregory M. Kurtzer}
\date{Draft technical report --- October 2026}

\begin{document}
\maketitle

\begin{abstract}
Can an expert-directed AI coding agent build a new kernel capable of running an
existing Linux userspace? Ginux demonstrates that, within a focused research
scope, the answer is yes. Kernel construction is well documented; the
experiment tests how quickly expert-directed AI can integrate established
mechanisms into a runnable system. Over eleven days, OpenAI Codex with GPT-5.6
Sol produced an independent, Rust-first x86-64 kernel containing approximately
139,000 retained lines of implementation and test code across 1,037 commits.
Ginux boots through UEFI, provides its own memory management, scheduler,
process model, filesystems, networking, devices, and Linux userspace
compatibility layer, and runs its controller as an ordinary ring-3 process.

The resulting system executes unmodified Alpine programs and completes a Rocky
Linux 10 systemd boot through \texttt{multi-user.target}, with systemd running
as PID~1 and an interactive console. It also executes the same sysbench binary
used on a stock Rocky Linux comparison system. Initial measurements exposed
severe performance defects. A short benchmark-driven optimization exercise
allowed Codex to profile the system, revise kernel hot paths, and bring the
tested CPU, memory, threading, and mutex workloads into broadly comparable
territory. Performance parity was not a primary goal, and the project devoted
only a small portion of its development time to optimization.

Once Linux userspace execution became practical, Ginux also provided a
platform for experimenting with kernel-native domains: isolated resource and
scheduling principals capable of booting their own distribution userspaces.
These domains were an outcome of the experiment rather than its original
purpose.

The larger result is both exciting and cautionary. An expert working with AI
can now build software as complicated as a Linux-compatible kernel in a
remarkably short time. That capability does not make a one-off kernel a
sensible foundation for production infrastructure. Linux represents decades
of human engineering across compatibility, hardware enablement, security,
standards, review, vendor support, community governance, and operational
experience. Ginux benefited from the luxury of a narrow research scope and
remains far from those requirements. For core infrastructure, the ability to
build something is only the beginning; shared standards and a durable
ecosystem matter more than the code alone.
\end{abstract}

\section{AI Built a Linux-Compatible Kernel. It Did Not Build Linux}

The experiment began with an ambitious research question: could an AI agent
build a kernel capable of running an existing Linux userspace? Within the
research boundary described here, the answer was yes. \project{} boots from firmware under QEMU,
provides its own memory manager, scheduler, process model, ELF loader, virtual
filesystems, networking, IPC, device paths, and Linux syscall translation, and
runs real Alpine and Rocky Linux components.

Textbooks, teaching kernels, production source, standards, and implementation
discussions document kernel construction extensively. This experiment does
not show first-principles invention; it tests whether expert-directed AI can
synthesize those mechanisms into a distinct architecture, diagnose failures,
and pass increasingly demanding behavioral gates.

\project{} is an independent kernel; Linux is its userspace compatibility
target. The distinction is visible in \texttt{uname}: a Linux-personality
domain reports \project{} as the kernel. ``Linux-compatible'' means that
selected unmodified Linux programs see enough of their expected ABI to run.
Compatibility is still partial.

The name is a deliberate joke in the same family as Linux. ``Linux'' combines
Linus and Unix; ``Ginux'' riffs on Linux, GPT, and Greg. For purposes of
authorial restraint, the ``G'' is treated as GPT.

The goal was research, not competition with Linux. The Linux kernel community
has spent decades doing the difficult work of supporting
hardware, preserving interfaces, reviewing security-sensitive changes, and
maintaining software people actually depend on. Eleven days of enthusiastic
AI-assisted development belongs in a very different category.

\section{What Ginux Is}

\subsection{A simplified boot architecture}

UEFI removes several assumptions inherited from the BIOS era. Firmware loads a
PE32+ application into memory, including all of its sections, through
\texttt{LoadImage()}~\cite{uefi211}. An operating system can therefore arrive
as a much larger payload instead of growing through a chain of bootstrap
loaders from a 512-byte boot sector. Firmware quality, available memory,
filesystem support, and PE/COFF representation still impose practical limits.

Ginux uses that freedom to boot a single \texttt{GINUX.EFI} image containing its
Rust-first kernel, required x86-64 assembly, embedded controller payload,
component catalog, and recovery metadata. There is no required host
distribution, separate bootloader, or separate initramfs. After leaving UEFI
boot services, the kernel establishes paging, interrupts, protection,
scheduling, capabilities, storage, and networking, then launches the embedded
controller as a normal ring-3 process. The controller is packaged with the
kernel but executes in userspace.

This packaging simplified an experiment that otherwise would have needed to
coordinate a bootloader, kernel image, initramfs, host root filesystem, and
userspace versioning. It also supported the project's immutability model: the
kernel, controller, initial authority, and boot-required components can be
measured as one artifact before execution. A production system would still
need a mature update, rollback, signing, recovery, and firmware-compatibility
story.

\subsection{Implementation anatomy}

Ring~0 contains the mechanisms that must enforce a system-wide invariant:
page tables and address spaces, scheduling, capabilities, IPC, interrupt and
timer handling, domain ownership, the Linux personality boundary, and the
trusted side of device and DMA control. The x86-64 implementation does not use
rings~1 or~2. Ring~3 contains the controller, Linux workloads, and isolated
native services. Embedding a program in \texttt{GINUX.EFI} controls how its
bytes arrive; the processor ring still controls its privilege.

The controller is a freestanding, statically linked Rust program using the
Linux ABI for ordinary process behavior and a versioned device/\texttt{ioctl}
interface for Ginux management. It parses commands, maintains domain and
network configuration, starts and observes workloads, and manages persistent
configuration and the OCI cache. It begins with administrative authority
defined by the sealed boot envelope, which also sets the outer limit on the
rights it can delegate.

Device support is deliberately split. The kernel discovers PCI devices and
retains interrupt-controller, MSI-X, IOMMU, and capability enforcement. The
prototype includes virtio block and network paths and demonstrates measured
Rust driver/protocol services in separate ring-3 domains with bounded MMIO,
DMA, queue, and packet authority. Capabilities and resources are tagged with a
domain generation so a crashed service can be quiesced, revoked, and replaced
without treating its successor as the same security identity. The prototype
demonstrates this design, while a general driver framework and hardware matrix
remain future work.

The filesystem side is similarly purpose-built. Kernel VFS and mount behavior
present domain-local roots assembled from verified OCI layers, a writable
overlay, and selected \texttt{tmpfs}, \texttt{procfs}, and \texttt{devfs}
semantics. A host-owned block volume preserves controller configuration and a
content-addressed image cache. Immutable file pages are shared within a domain
and copied when made writable. Small assembly boundaries enter and leave UEFI,
install exception, interrupt, and syscall entries, switch privilege and
address-space state, and provide ABI probes; policy and most mechanisms remain
in Rust.

\subsection{Controller, domains, and personalities}

The controller configures the host and creates workload domains. It manages
domain lifecycle, images, resources, networks, persistent configuration, and
the local OCI cache through a versioned control interface. Host administration
therefore remains in userspace even though the controller arrives inside the
boot image.

A \emph{domain} is a native Ginux kernel object with a broader role than an OCI
container or Linux namespace. It owns or is granted address spaces, a process tree,
capabilities, IPC objects, filesystem and mount views, networks, devices,
limits, lifecycle, and failure policy. OCI supplies a domain's initial
filesystem; Ginux supplies its isolation and execution. A single domain can
look like a conventional computer, with systemd as PID~1 and a distribution
userspace above it. Multiple domains share one kernel while retaining separate
kernel-owned identities and resources.

Domains are also scheduling principals. The implemented CPU scheduler chooses
the highest ready domain service class and schedules processes within that
class. The architecture extends that model to independent CPU, memory,
storage-I/O, and network-I/O classes, allowing one domain to receive
latency-sensitive service while another scavenges spare capacity. Complete
cross-resource QoS enforcement remains future work. The experiment establishes
the architectural boundary and the first part of the scheduling model.

A \emph{personality} defines the userspace contract visible inside a domain:
executable format, syscalls, process and signal behavior, VFS semantics,
devices, terminals, clocks, networking, and namespace expectations. Linux
x86-64 is the only implemented personality. BSD is a plausible experiment
because it could reuse the same domain, memory, scheduling, and device
mechanisms, but no BSD ABI was built or tested. Linux namespaces may eventually
subdivide a Linux domain; they would remain inside the stronger outer domain
boundary.

Storage follows the same separation. Domain roots may be assembled from
verified OCI layers and receive a boot-local writable overlay. Ginux also has
a persistent host-owned volume for controller configuration and a
content-addressed OCI layer cache, so a reboot need not redownload every image
or forget every domain. It currently provides selected tmpfs, overlay, procfs,
devfs, and persistent-volume behavior. Linux's broad filesystem ecosystem and
production storage guarantees remain outside the prototype.

\subsection{POSIX surface, identities, and permissions}

Linux syscall-number coverage alone says little about POSIX conformance. POSIX is
primarily a source and behavioral contract across libc, processes, files,
signals, terminals, clocks, synchronization, and IPC. The evaluated musl and
glibc userspaces exercise fork/exec/wait, path and descriptor operations,
pipes and FIFOs, signals, clocks, termios, sockets, futex-based threading, and
selected POSIX and System~V IPC. Ginux has only partial coverage and has yet to
run a complete POSIX conformance suite.

Each domain owns a sealed native capability table. A capability names one
kernel object and grants some combination of read, write, manage, and execute.
Initial authority comes only from the boot envelope; delegation can attenuate
but not expand it; handles are generation tagged, and root revocation removes
derived rights. Devices, DMA pages, queues, volumes, and management operations
can therefore be granted independently. A domain also owns its configured CPU
and memory budgets, address spaces, processes, IPC, filesystem/mount views,
networks, devices, lifecycle, and failure policy. CPU service classes are
scheduled today; complete memory and I/O contention enforcement is unfinished.

Inside that boundary, the Linux personality applies domain-local credentials
and permissions. The evaluated profile maps UID/GID~0 to kernel ID~100000 and
uses real/effective/saved IDs in signal, cross-process, and file-access checks.
The VFS implements mode, ownership, \texttt{umask}, and access operations used
by the package-manager path. The profile has one mapped identity, no Linux
capabilities, and denies many credential mutations. POSIX ACLs and permission
edge cases remain incomplete; no SELinux or other active Linux security module
enforces labels. Linux UID~0 cannot bypass the native capability table.

\subsection{Performance and benchmarking}
\label{sec:performance}

Performance testing began as a reality check. A matched single-vCPU harness fixed
the QEMU machine, memory, CPU, accelerator, commands, and measurement
boundaries. Boot timing ran from QEMU launch until systemd reported
\texttt{multi-user.target}. Four sysbench workloads then exercised the same
verified Rocky Linux 10 x86-64 executable in both systems: prime calculation
for CPU throughput, one-kibibyte memory transfers, repeated
\texttt{sched\_yield()} operations for thread scheduling, and mutex
contention. Workload timing excluded boot and image preparation. Rocky on
Linux used the official Rocky Linux 10.2 GenericCloud image from the upstream
Rocky project, prepared and booted locally as a qcow2 disk, with its stock
\texttt{6.12.0-211.16.1.el10\_2.0.1.x86\_64} kernel; Rocky on Ginux used the
Rocky Linux 10 UBI init image as a domain. The protocol and raw-result
requirements are recorded in
\repolink{docs/BENCHMARKING.md}{the comparative benchmark protocol}.

The first results were funny only because they were so bad. CPU and mutex were
already near or above the Rocky result, but memory reached only 48.390~MiB/s
against Rocky's 679.510~MiB/s, and the thread test managed 0.078 events/s
against 306.129---roughly 14 times and 3,900 times slower, respectively. The
benchmark was then turned into an acceptance gate. The project lead required
matched inputs, clarified the single-vCPU scope, and directed Codex to profile,
change the kernel, rerun the measurements, and keep only verified
improvements. Within that boundary, Codex selected the instrumentation and
implementation changes and iterated against repeated QEMU runs. This was the
same outer-steering and inner-agent procedure described in
Section~\ref{sec:methods}, applied to a performance problem rather than a
feature milestone.

Over the next few hours, the measurements exposed specific defects rather
than a single generally slow kernel. The thread path repeatedly selected a
just-preempted supervisory thread and later saved and restored a complete user
context even when no other thread could run. The memory test was dominated by
timestamp overhead: its one-kibibyte operations repeatedly crossed into the
kernel because Ginux had no vDSO. Scheduler selection, no-op yields, diagnostic
tracing, page-table validation, and the guarded clock path were tightened one
at a time, with regressions rejected by the existing verification suite. A
Linux-compatible vDSO and read-only vvar page then carried fast timekeeping
through the initial process and subsequent \texttt{execve()}. A second pass
made the vvar snapshot immutable for each execution image and replaced clock
division with fixed-point conversion and constant-time reciprocal
normalization. The thread median rose from 0.078 to 309.732 events/s, and
memory throughput rose from 48.390 to 620.580~MiB/s. An earlier profiling loop had also reduced
Ginux's internal Linux-init-to-console path from 15.344~s to a 4.08--4.45~s
range by removing a polling stall, quadratic frame scans, and eager copying of
immutable root-filesystem pages. The optimization history is recorded in the
\repolink{docs/PERFORMANCE.md}{performance record}.

The results tell three different stories. First, the CPU, single-thread yield,
and mutex tests reached approximate parity in this translated environment.
Read narrowly, those numbers show that the worst gaps came from implementation
defects that a benchmark-driven agent loop could find and substantially close.
Second, adding Linux-compatible
vDSO/vvar timekeeping raised memory throughput from 48.390 to 620.580~MiB/s,
leaving Rocky on Ginux 1.095 times slower than Rocky on Linux for the
one-kibibyte test. Most of the original gap was timestamp overhead rather than
raw copying; this TCG experiment cannot isolate the cause of the smaller
remaining difference. Third, the boot result compares two startup paths.
Ginux restores a cached filesystem and launches a domain directly. Rocky boots
from a local qcow2 disk through its general-purpose UEFI, kernel, initramfs,
and device-discovery path. The 3.31-fold result describes those paths rather
than overall kernel performance.

These TCG measurements show that Ginux can execute the same nontrivial Linux
benchmark and that guided autonomous iteration can turn catastrophic results
into broadly comparable ones for this narrow suite. A broader performance
claim would require identical userspace profiles, equivalent storage,
dispersion and confidence intervals, and x86-64 KVM measurements. Network,
IPC, multicore, storage, and security performance remain unmeasured.

\subsection{Implemented result and research boundary}

The prototype boots a unified x86-64 EFI image, runs its controller in ring~3,
acquires networking under QEMU, and pulls and caches OCI filesystems. It runs
Alpine musl/BusyBox and Rocky glibc programs, launches Rocky systemd through
\texttt{multi-user.target}, and retains independent process, address-space,
root, mount, and lifecycle state across multiple domains.

The ledger classifies all 375 Linux 6.12 x86-64 syscall numbers: 82 Complete,
245 Partial, and 48 Policy-denied. The counts show breadth rather than
completeness. Loader and process behavior, pseudo-filesystems, cgroups,
namespaces, IPv6, ioctl families, filesystems, and devices remain incomplete.
There is no GPU ecosystem, broad hardware support, stable third-party driver
ABI, independent security audit, native performance baseline, or general Linux
application guarantee.

These gaps define the research boundary. The project asked whether AI could
construct a kernel and carry a real Linux userspace across it. It answered
that question without pretending to replace decades of Linux engineering.
Useful ideas, including domains, may ultimately belong in established systems
rather than a Ginux deployment.

\subsection{Security implications}

Ginux and Linux expose compatible userspace interfaces through unrelated
kernel implementations. Their kernel-specific vulnerabilities and exploits
will generally differ. Exceptions may exist where a flaw arises
from shared hardware behavior, protocol semantics, executable formats, or an
ABI-level design rather than a kernel-specific implementation.

Userspace vulnerabilities are largely unaffected: the same vulnerable
application running inside a Ginux domain may still be exploited in the same
way. What changes is the boundary reached after exploitation. Domain policy
could deliberately restrict selected Linux or POSIX-compatible behavior. For
example, a domain could enforce an immutable privilege ceiling under which no
process can acquire more authority than the domain received at creation,
regardless of set-user-ID executables, capabilities, namespaces, or a
compromised privileged service.

The broader security idea is straightforward: explicit capabilities, per-domain
address spaces, W\textasciicircum X mappings, immutable executable pages,
generation-safe revocation, and IOMMU-confined DMA reduce ambient authority
and contain component failure. The prototype exercises several positive and
negative paths, including stale-generation rejection and driver teardown, but
it has not received an independent audit, side-channel analysis, whole-kernel
formal verification, or adversarial production testing. Follow-up research
should test whether the independent implementation and stronger domain
constraints reduce practical exploitation enough to outweigh the risks in a
new and comparatively immature codebase.

\section{Methods}
\label{sec:methods}

\subsection{From an idea to an executable plan}

The work began with a technical vision far more specific than ``build a
kernel.'' The target was an independently implemented kernel with a
normal Linux userspace, a small host, strong privilege boundaries, recoverable
services, and an operator experience that behaved like a system rather than a
demonstration. Sustained Q\&A examined what belonged in ring~0, what Linux
compatibility meant, how domains differed from namespaces, and what observable
result would count as success.

Expert steering continued throughout the project. Partial implementations
exposed decisions that the opening prompt could never have anticipated. The
project lead identified category errors, rejected results that looked
successful but behaved incorrectly, supplied Linux and provisioning context,
changed priorities, and defined the next useful endpoint. Those corrections
first became written architecture and then implementation requirements. This
kept the project focused on a working system instead of an impressive boot
transcript.

The first artifact was a collaborative architectural overview. The versioned
\repolink{ARCHITECTURE.md}{ARCHITECTURE.md} then developed the boot model,
kernel/userspace boundary, domains, authority, storage, devices, and acceptance
criteria in greater detail. The
\repolink{docs/LINUX-COMPATIBILITY.md}{Linux compatibility ledger} recorded
syscall and non-syscall behavior. The
\repolink{docs/NEXT-GOAL.md}{working goal},
\repolink{docs/USE-CASES.md}{use cases}, and
\repolink{docs/decisions/0001-native-domains-and-authority.md}{domain decision
record} kept both plan and rationale outside the chat transcript. These files
provided durable state for a long-running agent session and made architectural
drift visible.

\begin{samepage}
\subsection{Staged construction}

Repository history and the project plans show six broad, overlapping stages:

\begin{enumerate}[leftmargin=*,label=\arabic*.,topsep=0.5em,itemsep=0.4em,parsep=0pt]
\item \textbf{Boot and architecture.} Define the trust and domain model, build
  a unified x86-64 EFI image, exit UEFI boot services, establish a kernel stack,
  and inventory memory and ACPI state.
\item \textbf{Kernel mechanisms and hardware.} Add paging, frame ownership,
  exceptions, interrupts, the APIC timer, preemptive scheduling, capabilities,
  IPC, domain address spaces, PCI discovery, virtio paths, and IOMMU-mediated
  DMA confinement.
\item \textbf{Userspace control.} Enter ring~3, execute an embedded static
  controller as an ordinary userspace process, and expose versioned management
  operations for domains, networks, storage, and lifecycle.
\item \textbf{Linux execution.} Build an x86-64 ELF interpreter, PIE and dynamic
  loader support, process and signal semantics, virtual filesystems, terminals,
  sockets, and a growing Linux syscall surface.
\item \textbf{Distribution ingestion.} Add DHCP, DNS, TCP/TLS, OCI manifest and
  architecture selection, digest verification, layer unpacking, caching, and
  domain-local roots; then run Alpine and progressively larger Rocky Linux
  programs.
\item \textbf{Compatibility and system boot.} Turn discovered behavior into a
  Linux ABI test matrix, add persistence and multi-domain lifecycle tests, and
  use Rocky Linux systemd, service startup, and an interactive console as the
  compound integration gate.
\end{enumerate}
\end{samepage}

The stages built on one another: firmware entry preceded hardware
control; a bounded ELF executable preceded a general Linux process; synthetic
ABI probes preceded Alpine; Alpine preceded glibc-based Rocky Linux; and Rocky
programs preceded systemd. Each stage converted its failures into requirements
for the next revision. A boot message was only the beginning of a test.

\subsection{The closed-loop agent procedure}

Every milestone had an observable gate, progressing from EFI boot and a ring-3
controller through Alpine, OCI ingestion, Rocky binaries, systemd, and a
console. The agent iterated within a bounded goal, while expert control defined
the gate and interpreted the result. The method contained two coupled loops:

\begin{center}
\fbox{\parbox{0.91\linewidth}{
\textbf{Outer steering loop:} technical vision $\rightarrow$ architecture and
constraints $\rightarrow$ milestone and acceptance gate $\rightarrow$ expert
review of real behavior $\rightarrow$ correction, reprioritization, or
acceptance.\\[3pt]
\textbf{Inner agent loop:} implementation $\rightarrow$ build and QEMU run
$\rightarrow$ measurement and failure analysis $\rightarrow$ revision
$\rightarrow$ regression test.
}}
\end{center}

The performance work in Section~\ref{sec:performance} shows both loops in
practice. Human steering defined a fair comparison, rejected mismatched
measurements, fixed the single-vCPU boundary, and set ``close the gap without
weakening correctness'' as the gate. The agent then profiled, changed one hot
path at a time, rebuilt, ran QEMU, compared repeated samples, and either kept
or reverted each change. The large thread improvement emerged from autonomous
iteration inside that expert-defined test and acceptance boundary.

Codex selected implementations, edited the repository, compiled and booted the
system, analyzed logs, wrote tests, profiled failures, and revised within the
current gate. It also drafted documentation for review. Human direction
supplied the architecture, priorities, compatibility target, operator model,
definition of normal behavior, course corrections, and stopping decision.
Codex had broad implementation autonomy inside those boundaries.

Tests became progressively less synthetic: probes established mechanics;
Alpine exposed filesystem and process errors; Rocky exercised glibc and larger
mappings; systemd combined scheduling, epoll, signals, procfs, sockets, mounts,
credentials, timers, and consoles. Interactive testing reopened apparently
completed milestones whenever observed behavior was wrong. Rapid agent
iteration produced code; expert review decided when the result was useful.

The mechanics---written architecture, external plans, executable gates,
bounded iteration, evidence review, and recorded gaps---are reusable. They work
best when an experienced reviewer knows what to ask, which output to distrust,
how the target normally behaves, and which endpoint is valuable. The method
reduces implementation cost while keeping technical leadership central.

\subsection{Human steering and agent autonomy}

The project combined continuous human steering with broad agent autonomy.
Domain expertise supplied the objective, system vision, constraints,
compatibility standard, interpretation of failures, and acceptance judgment.
Codex proposed mechanisms, selected implementation details, wrote and tested
the code, and updated the working documents. The project lead kept the work on
course by recognizing incomplete answers, conceptual errors, and unhelpful
endpoints.

The conversation record makes the distinction concrete. An embedded initial
userspace became an ordinary ring-3 static process using the Linux ABI plus a
narrow management interface; embedding remained only a packaging property.
Domains became kernel-native boundaries with independent process, mount,
network, credential, capability, and resource state. OCI returned to its
actual role as image transport and filesystem content. These corrections
established the abstractions that shaped the rest of the implementation.

Operator testing was steering. Empty directory listings exposed process and
filesystem defects; a second domain exposed singleton state; systemd exposed
missing mount, procfs, socket, terminal, and event semantics; controller
latency exposed scheduling defects. Interpreting each symptom against normal
Linux behavior changed acceptance gates and often the architecture. Repeated
direction to test real workflows, stop at reviewable milestones, remove
regressions, and distinguish output from correct semantics materially shaped
the result.

Codex proposed other important mechanisms, including generation-tagged
capabilities, bounded control calls, copy-on-write handling, and
pre-authorized shared-page fast paths. They fit the human requirements for
speed, security, fault containment, and ownership. Architectural review
retained the shared-page fast path as an agent-derived optimization.

In practical terms, the division of work was:

\begin{enumerate}[leftmargin=*,topsep=0.5em,itemsep=0.45em,parsep=0pt]
\item Human direction set the Linux compatibility target, the stronger-than-
  namespace domain model, expected operator behavior, acceptance standard, and
  stopping point.
\item Codex designed and implemented the system within those requirements. It
  also proposed mechanisms such as generation-bound capabilities and the
  authorized shared-page fast path, which remained subject to architectural
  review.
\item Q\&A and hands-on testing refined the architecture. Human testing judged
  real behavior, while Codex converted those workflows into repeatable QEMU,
  ABI, lifecycle, and performance gates.
\end{enumerate}
\smallskip

The user-visible conversation is the most detailed record; repository history,
design documents, and tests provide corroboration. A
\href{https://github.com/gmkurtzer/ginux/blob/main/docs/paper/STEERING-PROVENANCE.md}{curated
steering chronology} accompanies the paper and records direct steering, agent
proposals, collaborative refinement, and corrections triggered by observed
behavior.

\section{Alternative: Starting with Linux}

A practical product effort would have had strong reasons to begin with Linux.
Namespaces, cgroups, KVM, device drivers, filesystems, security modules, and a
vast compatibility suite already exist. A Ginux-like controller could manage
an immutable Linux host, while a domain experiment could initially combine
those mechanisms and add scheduler, device, and resource-policy changes where
the existing abstractions proved insufficient. That route would have produced
broader hardware and application support much sooner.

It would also answer a different question. This experiment deliberately
removed Linux from the kernel side to test whether an expert-directed AI could
construct the machinery itself and discover a distinct outer isolation object.
Starting with Linux would shift the work from reimplementation toward
integration, hardening, measurement, and upstream-quality design. That may be
the more valuable implication: if AI can traverse the from-scratch path, an
expert can instead aim it at bounded improvements to a mature system, where
the ecosystem remains intact and the novel idea must survive existing review,
compatibility, and performance standards.

\section{Human Experts Are Critical for Great Outcomes}

Human expertise made Ginux possible. Codex dramatically shortened the path
from a technical decision to working code, while human direction supplied the
vision, priorities, and standard for success. Practical systems knowledge was
needed at every turn: choosing a Linux userspace contract, separating OCI
transport from runtime isolation, recognizing broken fork/exec behavior,
defining domain ownership, interpreting systemd failures, and distinguishing
convincing output from correct behavior.

The project direction drew on experience from Caos Linux, CentOS, and Rocky
Linux; the Singularity/Apptainer container ecosystem; the Warewulf and Perceus
cluster-provisioning ecosystems; and production infrastructure operations
~\cite{rockyAbout2026,ciqKurtzer2026}. That background shaped the distinction
between OCI transport and runtime isolation, the controller workflow,
persistent image caching, domain boot semantics, provisioning requirements,
the acceptance gates, and the decision to stop. It also made apparently
successful but semantically incorrect results easier to recognize. Each such
failure became a better test or an architectural correction. In systems
software, this judgment is as important as the ability to produce code.

AI also gives junior engineers a much shorter path to meaningful contribution.
They can explore unfamiliar code, generate tests, compare interfaces, and
implement bounded work at a speed that previously required much more
experience. Experienced engineers know which abstraction fits, which result
deserves another test, what compatibility means in practice, and when a local
success creates a system-wide liability. The best results pair AI's
implementation speed with an expert's ability to keep the work pointed at the
right problem.

The same lesson applies to project controls. Written architecture gives the
agent a stable target. Workflow-based gates measure behavior that operators
actually depend on, while external references and differential tests keep
compatibility claims grounded. Independent security review adds a separate
line of judgment. Together, these practices turn generation speed into
accountable engineering. AI expands who can build; human ownership determines
what deserves trust.

\section{Code Is Not the Moat}

Building a small working kernel is bounded. Sustaining a production kernel
means supporting diverse hardware and workloads, preserving interfaces,
repairing defects, coordinating contributors and vendors, and maintaining a
dependable release cadence. Code is comparatively easy; workflows,
compatibility, maintenance, and community are hard.

Ginux used \estimatedcost{} in API calls---about USD~7.71 per commit or
USD~0.058 per retained, non-generated implementation/test line. Those are
rough comparisons, but the contrast matters: code can now be generated
cheaply, while its compatibility and maintenance burden can last for years.
The USD~8,000 produced a prototype. Trust, industry integration, and long-term
maintenance would cost far more.

AI is already applying similar pressure to application software. In October
2026, ArtCraft published early Rust implementations modeled on seven Adobe
Creative Cloud applications, developed with heavy use of Claude
~\cite{artcraft2026}. Independent hands-on testing found recognizable tools
and striking development speed, but missing features and basic failures kept
them from replacing the originals~\cite{creativebloqArtcraft2026}. Visible
capabilities are cheaper to reproduce; full behavior, integrations, support,
and trust remain hard.

This pressure will likely be strongest above middleware and orchestration,
where applications can be replaced without moving an entire hardware and
software ecosystem. Foundational software can also be reimplemented, but
enterprise infrastructure is selected through standards, interfaces,
certification, hardware enablement, community continuity, and commercial
support. Novelty has limited value without that ecosystem.

Linux is the clearest example. Its value extends far beyond the source needed
to boot a shell. It includes stable expectations across processors,
filesystems, devices, hypervisors, distributions, security teams, silicon
vendors, cloud providers, and application developers. Ginux starts without
that foundation: it lacks a vendor-supported GPU stack, a physical-hardware
matrix, broad filesystem support, a standards body, and a community committed
to keeping yesterday's programs working tomorrow. AI may help build the
technical pieces. Adoption still requires independent organizations to agree
on and support the same contracts.

\section{Conclusion}

Ginux shows how dramatically expert-directed AI can compress a substantial
systems project. In days, it produced a new kernel, ran real distribution
userspaces, and explored kernel-native domains: rapid integration, not the
invention of kernel engineering itself.

That result belongs beside clear limits. Ginux lacks the maturity and ecosystem
required for production infrastructure; Linux remains in a different league.
Useful ideas may be better carried into established systems than used to ask
the world to adopt another kernel.

AI can build code, including code deep in the systems stack. Ginux demonstrates
how far that capability has advanced, but it also demonstrates where code
generation stops being the central problem. Core infrastructure derives its
value from compatibility, standards, hardware support, security practice,
community trust, and long-term operational ownership. Linux earned those
qualities through decades of human engineering and continuous releases across
an enormous hardware and workload surface. Ginux reproduced a narrow portion
of the code; it did not reproduce that institution. AI may dramatically reduce
the cost of implementation, but the ability to build a new foundation is not,
by itself, a reason to replace the one an ecosystem already trusts.
