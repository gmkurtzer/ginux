\title{\textbf{Ginux: What an AI-Built Linux-Compatible Kernel Reveals About the State of AI Systems Engineering}}
\author{Gregory M. Kurtzer}
\date{Draft technical report --- October 2026}

\begin{abstract}
We asked whether one AI coding agent could build a new kernel capable of
running an unmodified Linux userspace. In eleven days, one persistent
\modelname{} task produced \project, an x86-64 Rust and assembly kernel that
boots through UEFI, runs its controller in ring~3, ingests OCI images, executes
Alpine, and launches Rocky Linux 10 systemd as PID~1. The evaluated commit
contains about 139,000 retained, non-generated lines of implementation and test
code across 1,037 commits. Estimated API cost was \estimatedcost.

The prototype answers the construction question. It does not meet the standard
of a production kernel. Its own ledger marks 82 of 375 Linux x86-64 syscalls
complete, 245 partial, and 48 policy-denied. GPU drivers, stable driver ABI,
native performance results, independent security review, and general
application compatibility are missing. A manual lifecycle test also broke a
workflow that narrower agent-authored tests had declared complete. Ginux
demonstrates rapid construction of a serious systems prototype. Trust still
depends on independent tests, standards, review, and long-term ownership.
\end{abstract}

\section{Question and scope}

AI coding demonstrations usually end when a program compiles or passes a
bounded test. Kernels are less forgiving. They join instruction entry, memory,
concurrency, executable loading, filesystems, devices, process lifecycle,
networking, and cleanup. A shell prompt proves only the path that reached it.

We created \project{} to test whether an agent could build enough of that stack
to run existing Linux userspace. A secondary question emerged during design:
could a kernel-native \emph{domain} serve as the outer boundary for ownership,
resources, devices, failure, and Linux compatibility? Linux namespaces would
remain available inside a Linux-personality domain.

We stopped when the construction result was clear. The system never became
deployable. The fixed artifact is commit \evaluatedcommit{}, dated October 20,
2026. All measurements refer to that commit and its QEMU profiles. Later fixes
are outside the evaluation.

The name \project{} follows the Linux tradition. The ``G'' stands for GPT, at
least officially; this interpretation also keeps the author's head from
getting any bigger.

\section{Method}

Approximately 99\% of the implementation came from one persistent Codex task
using \modelname{}. That is an author estimate because provider-level task and
token exports were not archived. This was one longitudinal task, not an army
of agents, although the host may have compacted old conversation into context
summaries.

The human set architecture, requirements, acceptance behavior, and stopping
points. Codex chose implementations, edited the repository, built it, booted
QEMU, interpreted failures, wrote tests and documentation, and committed
checkpoints. Direction was task-level: ``boot this image and make this workflow
work,'' not a sequence of code edits.

Versioned documents carried decisions that could not safely live in chat
history. The architecture document defined the system and trust boundaries;
the Linux compatibility ledger tracked syscall and non-syscall behavior;
roadmaps, decision records, and performance notes recorded milestones and
known limits. The agent consulted these files with an active plan. They reduced
context drift but were not independent specifications: the same agent helped
write them.

The working loop was:

\begin{center}
\fbox{\parbox{0.91\linewidth}{
requirement $\rightarrow$ observable benchmark $\rightarrow$ implementation
$\rightarrow$ build and QEMU run $\rightarrow$ log analysis $\rightarrow$
revision $\rightarrow$ human test $\rightarrow$ signed commit.
}}
\end{center}

This resembles execution-feedback work in code generation~\cite{chen2021codex}
and repository tasks such as SWE-bench~\cite{jimenez2023swebench}, but the
specification and tests here evolved with the artifact. This shortened each
iteration while allowing the agent to satisfy weak benchmarks precisely.

One failure makes the point. Separate tests showed that a detached Rocky domain
returned control and that an attached start reached a login prompt. They did
not test the complete sequence of detached start, attach, detach, reattach,
stop, and restart. Codex marked the work complete. The author then ran that
sequence; cleanup failed with three Linux processes still live. Implementation,
test authorship, and verdict had shared the same blind spot.

\section{Artifact and results}

\project{} boots as a unified x86-64 UEFI image without a host distribution or
initramfs. The kernel establishes its own page tables, protection state,
interrupts, scheduler, memory ownership, capabilities, IPC, device paths, ELF
loader, and personality objects. A static controller runs in ring~3 and uses a
versioned control interface. OCI supplies image transport and filesystem
assembly~\cite{ocispec}. Ginux provides the runtime and isolation boundary.

The Linux personality follows the Linux 6.12 x86-64 syscall table
~\cite{linux612syscalls}, Linux UAPI and man-pages~\cite{linuxmanpages}, and the
x86-64 psABI~\cite{x8664psabi}. It supports ELF executables and selected PIE,
dynamic interpreters, virtual memory, processes, threads, signals, descriptors,
filesystems, sockets, terminals, and partial pseudo-filesystems. The loader uses
the image's \texttt{PT\_INTERP}; there is no musl or glibc mode.

A domain owns its address spaces, process tree, capabilities, IPC, filesystems,
networks, devices, limits, lifecycle, and failure policy. Unlike Xen
~\cite{barham2003xen}, it does not carry a guest kernel. Unlike seL4
~\cite{klein2009sel4}, Ginux has no proof. The design ran Linux processes and
kept per-domain state, but its isolation and QoS claims were not tested under
attack or contention.

Development moved from synthetic ABI probes to Alpine, Rocky glibc utilities,
and finally systemd. Each workload widened the real contract. Alpine found
filesystem, working-directory, and fork/exec defects. Rocky exercised dynamic
loading and mappings. systemd combined scheduling, epoll, signals, procfs,
mount identity, Unix sockets, timers, credentials, and console lifecycle.

LOC says nothing about correctness. The scale instead exposes the review
problem. One agent
created privileged code faster than one human could inspect it. Each parser,
state transition, unsafe operation, syscall emulation, and cleanup path adds
work for threat modeling, fuzzing, compatibility testing, and maintenance. In
a kernel, a small ownership or dispatch error can cross every workload. Fast
generation can accumulate assurance debt just as quickly as code.

\subsection{Compatibility, performance, and security}

The ledger covers all 375 Linux 6.12 x86-64 syscall numbers: 82 Complete, 245
Partial, 48 Policy-denied, and zero Missing. Zero Missing only means the table
does not fall through to a default \texttt{ENOSYS}. Static PIE without an
interpreter, broader loader and NSS behavior, process semantics, procfs, sysfs,
cgroupfs, vDSO/vvar, IPv6, namespaces, and ioctl families remain incomplete.
Unmodified Alpine shells run. Rocky glibc utilities run. A Rocky UBI init image
can launch systemd and reach a console login on selected paths. Arbitrary Linux
programs are not covered by that evidence.

Profiling under x86-64 QEMU TCG on Apple Silicon reduced Linux-init-to-console
time from 15,344~ms to a two-run median of 4,082~ms by fixing Unix-socket
polling, quadratic frame-reference scans, and immutable-rootfs duplication.
Warm OCI restore and publication took another 2.7 and 3.5 seconds. The final
manual detached-start run took 13,833~ms and then hit the cleanup bug. KVM and
identical-hardware Linux comparisons were not run.

Security mechanisms include capabilities, W\textasciicircum X mappings,
guarded stacks, generation-tagged ownership, selected fault cleanup,
SMEP/SMAP/UMIP setup, and IOMMU paths. No independent audit, sustained hostile
testing, or proof exists. Ginux cannot load the existing GPU-driver ecosystem
or promise stable \texttt{.ko} compatibility.

\section{What we learned}

The agent worked across UEFI, assembly, paging, interrupts, Rust kernel code,
ELF, Linux ABI behavior, network and block devices, OCI, shell automation, CLI
design, documentation, and profiling. It recovered from many failures and
turned distribution behavior into new tests. That breadth, across roughly
139,000 retained lines, is beyond autocomplete.

Its judgment was less reliable than its construction. Codex sometimes pursued
a marker instead of the operator workflow, reported success after adjacent
tests passed, blurred image transport with execution, and increased static
capacities before implementing dynamic behavior. Long execution loops also
made it reluctant to stop. Written architecture and plans helped, but a single
agent still shared assumptions across code, tests, and status reports.

The cost estimate is about USD~7.71 per commit or USD~0.058 per retained
non-generated implementation/test line. These ratios are curiosities. A short
scheduler repair can matter more than a generated table, and a retained bug is
as cheap per line as correct code. We did not measure active human hours. The
experiment measures the cheap production of one prototype. Integration,
review, compatibility, incident response, and years of maintenance remain
unpriced.

Domains also survived contact with implementation. They organized controller
authority, service ownership, Linux state, address spaces, consoles, and
workload records without a guest kernel. Resource enforcement, network and
filesystem isolation, lifecycle reliability, and QoS remain unfinished. The
idea is feasible enough to study. This prototype offers no basis for replacing
namespaces, containers, or virtual machines.

\subsection{Security and the software supply chain}

The same model family can audit old code as well as produce new code. In 2026,
research involving GPT-5.6 Sol helped establish the critical impact of a PHP
engine state-lifecycle flaw. The advisory describes stale request-owned global
state leading to use-after-free and unauthenticated remote code execution,
scored 9.2~\cite{phpStaleState2026}. OpenAI reported that a Calif researcher
used GPT-5.6 Sol and warned that similar capability can also accelerate
offensive tooling~\cite{openaiPatchPlanet2026}.

The PHP Foundation supplies the useful detail. Developers had recognized the
underlying out-of-memory problem in 2024, but a fix stalled over compatibility,
denial-of-service risk, extension impact, decision process, and staff time.
AI-assisted reports later exposed the RCE path. The team also processed more
than 100 reports that were invalid, duplicate, or irreproducible. Humans made
each decision and wrote each patch~\cite{phpFoundation2026}.

Ginux and PHP expose the same bottleneck. Machines can generate code and find
defects faster than maintainers can validate findings, choose compatible
repairs, coordinate disclosure, deploy updates, and support old releases.
Machine-speed output now runs ahead of human-speed assurance.

\section{Limits and controls}

This is one project, model, author, architecture, and eleven-day period. The
author directed and evaluated it; Codex wrote much of the code, tests,
documentation, and draft prose. Manual tests were opportunistic. Cost and the
99\% share are estimates. Commit count measures activity, not effort. The
system ran mainly through translated x86 QEMU on Apple Silicon. Real hardware,
KVM, other architectures, hostile workloads, broad package suites, and GPU
drivers were not evaluated.

Future work needs independent oracles. Compatibility claims should link to
Linux differential tests and external conformance suites. Security work needs
a threat model, unsafe-code inventory, fuzzing, adversarial review, and a
reviewer who did not author the implementation. Lifecycle, cleanup,
concurrency, exhaustion, and tail-latency tests should cover complete operator
workflows. Builds, prompts, billing records, image digests, and raw logs should
be reproducible and archived. A release also needs named owners for later
compatibility and incidents.

Separate implementation, compatibility, security, and acceptance agents might
reduce self-validation. Copies of one model can still repeat one another's
blind spots. Independence must also exist in the tests and incentives.

The project is Apache-2.0 and intended for public release. Publication should
archive commit \evaluatedcommit{}, a source manifest, the compatibility ledger,
benchmark logs, the development transcript, billing evidence, the detached
lifecycle failure, and the exact line-count commands.

\section{Conclusion}

Ginux reached the stopping point for which it was built. One persistent Codex
agent, given architecture, tasks, documentary memory, and machine feedback,
created a kernel that boots from firmware and runs real Linux distribution
components. The author guided goals and rejected bad conclusions without
specifying the code line by line.

Ginux cannot guarantee Linux program behavior, driver compatibility, security,
or native performance. The experiment establishes that an AI-guided agent can
vibe-code an operating-system prototype. Running production workloads on this
evidence would be reckless.

AI can build code. Our remaining problem is deciding what the code can do, how
well it does it, and who keeps those claims true after the session ends.
