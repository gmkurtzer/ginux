# Contract maintenance lock

## Source

Human direction after Gate 12.25 to provide a safe host-side maintenance mode.

## Goal

Let an operator explicitly unlock a stopped instance for maintenance that its
normal contract would deny, then relock it before ordinary use, with the state
visible and persistent.

## Approved scope

- Add top-level `ginux lock NAME` and `ginux unlock NAME` commands.
- Default every new and existing instance to locked contract enforcement.
- Persist lock state as host deployment state, not portable recipe content.
- Require the instance to be stopped before changing lock state.
- In unlocked maintenance state, relax configurable contract restrictions for
  supported operations while retaining Ginux virtualization, mediation,
  unsupported-operation denial, host identity reduction, `NoNewPrivs`, and all
  non-bypassable host-boundary invariants.
- Display `locked` or `unlocked` in `ginux list` and `ginux status` and emit a
  prominent warning when an unlocked instance starts.
- Add deterministic CLI, persistence, policy, and Rocky maintenance tests plus
  operator documentation.

## Non-goals

- Disabling Ginux, directly executing unsupported operations, granting host
  credentials, exposing host `/proc` or `/sys`, or weakening mandatory host
  containment.
- Editing the portable instance recipe when lock state changes.
- Allowing a running instance to change enforcement state.

## Acceptance criteria

- New instances and legacy deployment-state files without a lock record are
  treated as locked.
- `ginux unlock NAME` and `ginux lock NAME` work only while stopped, persist
  atomically, and are idempotent.
- `list` and `status` show the effective lock state, and starting unlocked emits
  a warning that contract maintenance mode is active.
- Locked execution uses the unchanged recipe contract; unlocked execution
  admits supported maintenance operations such as package updates while still
  denying unsupported and mandatory host-authority operations.
- Relocking restores the exact recipe contract without modifying the recipe.
- Malformed deployment state fails closed and no failed update changes state.
- Existing lifecycle, contract, virtual filesystem, and systemd behavior
  regressions remain green.

## Decisions and limitations

- `lock`/`unlock` describes whether the recipe contract is enforced and is more
  direct than “secure” or “enable.”
- Unlock is an explicit maintenance state, not an enforcement bypass: Ginux
  continues to own virtual kernel state and deny unsupported authority.
- Lock state belongs to host deployment state because it is an operational
  choice, not a portable workload requirement.
