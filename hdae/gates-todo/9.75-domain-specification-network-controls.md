# Domain specification and network controls

## Source

Human direction on 2026-11-04 following approval of Gate 9 host-shared
networking.

## Goal

Provide one comprehensive, versioned domain specification that controls domain
identity, startup, access, storage, devices, resources, networking, policy, and
lifecycle, with predictable command-line overrides and explicit network
attachment and port-routing behavior.

## Approved scope

- Extend the strict TOML domain configuration selected in Gate 4 rather than
  creating a parallel format.
- Cover hostname and identity, image and init, environment, resources, devices,
  volumes and host mappings, access, network attachment, port policy, contract,
  audit, failure behavior, and pre-boot hooks.
- Let the domain select one versioned contract base template, include additional
  versioned capability templates, and provide explicit allow or deny overrides
  using the bounded selectors defined by Gate 10. Keep detailed operation
  definitions in the contract registry rather than embedding an exhaustive
  syscall or ioctl table in every domain file.
- Apply one precedence rule: built-in defaults, then configuration file, then
  command-line overrides.
- Normalize and validate file and CLI values through one typed path and record
  the immutable effective configuration before startup.
- Retain Gate 9's host-shared default when no network setting is present.
- Allow selection of a host interface or source address, including an alias or
  additional address such as `eth0:1` when the host exposes it.
- Treat a selected host attachment as shared in full. Multiple domains may use
  the same attachment just like multiple host applications, and untranslated
  address/port binds retain normal first-successful-bind ownership.
- Configure inbound and outbound port allow/deny policy.
- Configure explicit port translation, including a mapping such as host
  device-or-address port `8080` to domain port `80`.
- Preserve normal bind-conflict behavior for untranslated shared ports.
- Define pre-boot hook execution context, authority, ordering, failure policy,
  timeout, environment, and audit behavior before executing hooks.

## Non-goals

- A graphical configuration editor, remote control plane, live migration, or
  runtime mutation of the initial effective configuration.
- Automatic firewall discovery, arbitrary policy programs, or silently
  granting host authority to domain hooks.
- Replacing the versioned ABI contract defined in Gate 10.

## Acceptance criteria

- A complete valid domain file produces one normalized effective configuration
  containing every approved configuration class.
- CLI values override only the named file values; unspecified file values and
  defaults remain intact, and the recorded effective configuration reflects
  the exact result.
- A domain can select a versioned default contract, add approved templates, and
  apply exact or glob-based restrictions and grants. The recorded effective
  configuration identifies those inputs and the immutable expanded contract
  digest produced by Gate 10.
- Domain and CLI overrides use the same typed selector model. Invalid,
  unmatched, ambiguous, or unsupported selectors fail before startup; the CLI
  cannot create an unrecorded policy path.
- Unknown fields, invalid combinations, unavailable interfaces or addresses,
  conflicting port mappings, unsafe volume mappings, and invalid hooks fail
  before domain startup with actionable errors.
- Omitting network configuration preserves Gate 9 host-shared behavior.
- Selecting a host interface or source address causes mediated traffic to use
  it or fails closed when the requested attachment is unavailable.
- Ingress and egress policy allow and deny the configured cases, and denial
  prevents the corresponding host effect.
- Port translation delivers traffic from the configured host
  device-or-address and port to the configured domain port without exposing
  unrelated ports.
- A mapping such as external `eth0:1:8080` to domain port `80` is owned and
  mediated by Ginux, while the domain continues to address its service as port
  `80`.
- Concurrent shared or translated binds have deterministic conflict and
  cleanup behavior; released mappings become reusable after teardown.
- Hook ordering, context, authority, timeout, failure, and audit semantics match
  the approved model and cannot bypass normalized configuration or mediation.
- `make demo-gate-9.75` demonstrates file configuration, CLI overrides,
  effective-config output, interface/source selection, allowed and denied
  traffic, port translation, conflict handling, hook behavior, and cleanup.

## Decisions and limitations

- Strict, versioned TOML remains the file format selected in Gate 4.
- Gate 9.75 owns how a domain selects and overrides a contract. Gate 10 owns the
  catalog, template contents, selector expansion, conflict resolution, and
  enforcement. The domain configuration records the resulting contract digest
  without duplicating the expanded rule table.
- Gate 9 establishes host-shared networking and normal socket conflicts. This
  gate adds selection and control without changing the central mediation
  invariant.
- The human must approve the pre-boot hook execution and authority model before
  that portion is implemented.
- The existing host helper executes as root, assembles the domain filesystem,
  and launches the runtime. A hook executed directly by that helper would be
  arbitrary trusted host code and part of the Ginux trusted computing base;
  it is not equivalent to a mediated hook executed as a managed domain task.
- Human direction on 2026-11-06 selected only mediated domain-context hooks.
  Hooks run after declarative root/resource preparation and before init under
  the domain's contract, identity, filesystem, device, and network views. Host
  hooks are unsupported.
